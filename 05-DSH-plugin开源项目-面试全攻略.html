05 · DSH-plugin 开源项目 —— 面试全攻略

三遍读法：第一遍读各节【先用大白话理解】；第二遍读【展开讲】；第三遍自测第 4 章问答库。这个项目是简历上唯一有真实代码可看的资产——面试官可能当场点开 GitHub，所以每个细节都要能讲到本文档的深度。代码已 clone 到 /tmp/DSH-plugin/ 可随时查证。

1. 口语稿

30 秒版

我给 DeepSeek Harness——DeepSeek 官方开源的命令行 AI 工具——写了两个插件，都在我的 GitHub 上。一个是计费统计插件：拦截每一次模型调用，按官方定价自动算花了多少钱，支持峰谷分时电价，还能看缓存命中率和当前对话的上下文占用；另一个是自升级插件：一键检查官方更新、合并、构建，失败可以回滚。两个插件都是零依赖纯 JavaScript，装的时候不用跑安装、没有供应链风险。起因是我自己重度使用这个工具，计费不透明和手动升级是自己的痛点，就自己动手解决了。

2 分钟版（面试官说”详细讲讲”时）

先说背景：DeepSeek Harness 是 DeepSeek 官方开源的终端 AI 助手，支持插件机制。我用它的过程中有两个痛点：一是 API 按 token 计费，但工具不告诉你花了多少钱、缓存帮你省了多少；二是工具本体是源码方式安装的，官方更新后要手动 pull、装依赖、构建。

计费插件的核心是一次”无感拦截”：模型的回答是流式一块块返回的，我在数据流上包了一层——每一块原样透传给宿主（用户完全无感知），流的最末尾有一块”账单”数据（本次输入输出各多少 token），截下来记账。记账放在 finally 里保证不漏，再包一层 try/catch 保证统计挂了也不影响对话。计费支持峰谷电价——官方高峰时段全价、空闲半价，和居民用电分时电价同构；缓存命中的输入价格约为未命中的 1/120，所以专门算了缓存命中率给用户看。存储用两份文件：jsonl 明细账本（只追加不改，写崩最多坏一行）加 summary 汇总报表，就是事实表加汇总表的结构。

升级插件最有意思的设计是”是否最新”的判定：一开始想比较本地和官方的版本号是否相同，但本地永远领先官方几个自己的定制提交，这么比会天天误报。改成”落后计数”——本地落后官方的提交数为 0 就是最新，同时如实显示”本地领先 N 条”。另外做了回滚锚点、脏工作区拒绝升级、端点只监听本机这些安全闸门。

这两个插件让我完整走了一遍”自己是用户→发现痛点→设计→发布维护”的闭环，也算把异步流处理和 Git 工程化用在了真实场景里。

2. 先用大白话理解：这两个插件各干了什么

计费插件 dsh-usage-meter = 给水管装水表

你天天用 DeepSeek 的 AI 干活，就像天天用水——但水厂（API）按吨收费，你家却没有水表：一个月下来不知道用了多少、花了多少、哪些是浪费。

这个插件就是在水管上装了一块智能水表：

  • 用水量（token 统计）：每次用水自动记录——多少是冷水（新输入）、多少是循环水（缓存命中，超便宜）、多少是排出去的（输出）；
  • 电费单（费用计算）：按自来水厂的峰谷水价自动算钱——白天高峰全价、深夜半价，账单分时段给你列清楚；
  • 省钱报告（缓存命中率）：告诉你循环水占多少比例——命中率越高越省钱；
  • 油表（上下文占用）：对话有容量上限（就像油箱），它告诉你油箱还剩多少、大约还能聊几条消息。

升级插件 dsh-updater = 给房子做”一键装修更新”

你的房子（DSH 工具本体）是源码盖的，开发商（官方仓库）经常出新版本，但你自己还改过几处装修（定制提交）。以前每次更新要手动：看有没有新版 → 拉代码 → 合并（还不能弄丢自己的装修）→ 装材料 → 施工。

这个插件把这些做成一键 + 可反悔：

  • 检查更新：自动对比”开发商比我新了几版”——注意不是比”版本号一不一样”，因为你自己改过装修，版本号永远对不上，比错了会天天谎报”有新版”；
  • 一键升级：合并新代码 → 装依赖 → 构建，全自动；
  • 绝不弄丢你的装修：只合并、绝不强推覆盖；万一合并打架，自动撤回现场再报错；
  • 可以反悔：升级前先拍张照（记下升级前的位置），盖砸了一键回到拍照那一刻。

3. 展开讲：会被问到的技术点

3.1 插件机制：怎么”挂”到宿主上的

大白话：像手机装 App——商店（宿主 DSH）提供安装位和系统服务，App 声明要什么权限，装上后开始干活。

展开：插件入口只有一行导出 module.exports = { name, inject: ['commands'], apply }。inject 声明需要的宿主服务（这里是斜杠命令注册表）；宿主装载插件时调用 apply(ctx)，把上下文递进来，插件在里面挂事件监听、注册命令。这是典型的控制反转（和 FastAPI 装饰器同一个思想：你提供零件，框架负责调用你）。

3.2 流拦截：核心中的核心（必考）

ctx.on('llm/stream', (options, next) => {
  const stream = next()              // 拿到原始数据流
  return (async function* () {       // 返回包装过的流
    let usage = null
    try {
      for await (const chunk of stream) {
        if (chunk.type === 'usage') usage = chunk.usage  // 流末尾的账单
        yield chunk                  // 原样透传, 一个字节不少
      }
    } finally {
      if (usage) {
        try { recordCall(options, usage) } catch (e) { /* 只打日志 */ }
      }
    }
  })()
})

大白话：大模型的回答像水管的水流，一块一块流过来。插件在水管上装水表：水照常流（yield 透传，宿主完全无感），表只管计数——流的最末尾有一块”账单”（type=usage 的数据块，带本次 token 明细），顺手截下来。

三个技术点（每个都是追问弹药）： 1. 流式响应（Streaming）：模型回答不是一次性返回的，是分块流式吐出，降低首字等待；async generator（异步生成器）是 JS 里处理流的标准姿势——for await 逐块消费、yield 逐块产出； 2. finally 记账：不管流正常结束还是中途抛错，finally 必然执行——保证”调用发生了就一定被统计”； 3. 统计失败不影响主流程：recordCall 包 try/catch，磁盘坏了也只是日志一句错。监控类代码第一原则：自己死不能拉着业务死——与美团巡检”失败登记不谎报”同一价值观，面试可互相呼应。

3.3 峰谷计价：和生活经验完全同构

function bandOf(tsMs) {                       // 每次调用按时间戳判断计价带
  if (tsMs < PEAK_START_UTC) return 'legacy'  // 调价日前 = 旧价
  const h = new Date(tsMs).getUTCHours()
  if ((h >= 1 && h < 4) || (h >= 6 && h < 10)) return 'peak'  // 北京时间 9-12、14-18 = 峰
  return 'offpeak'                            // 其余 = 谷(半价)
}

大白话：和居民峰谷电价一模一样——白天用电高峰贵、深夜便宜，引导错峰。DeepSeek 官方同理：高峰时段全价、空闲时段半价，引导把不急的任务挪到夜里。

展开：费用 = tokens ÷ 1,000,000 × 单价（官方按”每百万 token 多少元”定价），三个桶分别算再相加：未命中输入（全价）、缓存命中输入（超便宜，约为未命中的 1/120）、输出。缓存命中 = cacheRead + cacheWrite tokens；多轮对话把历史上下文重发，服务端认出”这段缓存过”就按超低价计——这就是”长对话为什么越到后面越贵”以及”缓存为什么省钱”的量化答案。

3.4 存储：明细账本 + 汇总报表

大白话：两本账——流水账（每笔一行的明细，只添不改）和总账（随时可看的汇总报表）。

展开： - records.jsonl（明细）：JSON Lines 格式，一行一条 JSON，append-only。为什么不用数据库：追加写天然安全（写崩最多坏最后一行）、纯文本肉眼可查、按行读天然可流式——单机个人工具的最优解，上 SQLite 是杀鸡用牛刀； - summary.json（汇总）：每次记账后重算的总账——累计、按模型分组、按会话分组、按计价带分组、最近一次上下文快照。读报表不用重放全部明细——和数仓”事实表 + 汇总表”同一个思想（可与中青旅 Text-to-SQL 的数仓知识呼应）。

3.5 命令与上下文油表

  • /usage：Markdown 报表（费用分旧价/峰/谷三段、token 三桶、缓存命中率、按模型表格）；
  • /usage context：上下文占用——已用 / 1,000,000（模型上下文窗口）= 百分比，剩余多少、约还能聊几条消息（剩余 ÷ 1500）。把”上下文窗口”这个抽象概念变成用户可感知的油表。

3.6 updater 的”是否最新”判定：最值得讲的设计决策

大白话：判断”要不要更新”，最直觉的做法是比”我家版本号和开发商的一不一样”——但你家自己改过装修，版本号永远对不上，天天谎报”有新版”（和”狼来了”误报一个性质）。正确做法：数”开发商比我新了几版”——落后数为 0 就是最新，同时如实显示”我领先 N 条自己的定制”。

展开：git rev-list HEAD..origin/branch 的计数为 0 即最新（behind 计数），不比较 HEAD 指针本身。这是”判定指标选错，报警永远不准”的真实案例，与美团误报治理（指标和丢包分布错配）同一方法论，面试串起来讲非常加分。

3.7 updater 的安全设计（必考”考虑过什么安全”）

  1. 回滚锚点：升级前把 merge 前的 HEAD 记入 ~/.dsh/dsh-updater.state.json，构建失败或反悔时 reset 回锚点重构建——破坏性操作必须可撤销；
  2. 只 merge、永不 reset –hard 远端：保护本地定制提交；merge 冲突自动 git merge --abort 恢复现场再报错；
  3. 升级前安全检查：工作区有未提交修改→拒绝；detached HEAD→拒绝；同时只允许一个升级在跑（并发互斥）；
  4. 端点只监听本机（loopback）：这些端点会执行 git/pnpm 命令，暴露到局域网等于把家门钥匙发给邻居。信任判定看 socket 地址 + Host 头，永不信任 X-Forwarded-For（可伪造的转发头）。

3.8 工程决策：零依赖

两个插件 package.json 无任何 dependencies、无构建步骤。理由：插件安装者不用跑 npm install（避免供应链攻击面）、加载快、维护简单。面试一句话：“插件越小，可信面越大”。

4. 问答库

Q1. 为什么做这个项目？ > 自己是 DeepSeek Harness 的重度用户，两个痛点：计费不透明（不知道花了多少、缓存省了多少）、源码安装升级麻烦。自己写插件解决——“自己是用户”是开源项目最真实的动机，也让我完整走了一遍发现问题→设计→发布→维护的闭环。

Q2. 怎么拦截每次模型调用的？（核心题） > 在 llm/stream 事件上包一层：拿到原始流后返回包装的异步生成器，逐块透传（宿主无感），流末尾 type=usage 的账单块截下来，在 finally 里记账（保证异常结束也统计到），记账再包 try/catch（统计失败绝不影响对话）。本质是在数据流上装了一块”水表”：水照常流，表只管计数。

Q3. 峰谷计价怎么实现的？ > 和居民峰谷电价同构：按每次调用的时间戳判断计价带——调价日前旧价、北京时间 9-12/14-18 峰时全价、其余谷时半价。费用按三个桶算：未命中输入全价、缓存命中输入约为其 1/120、输出按输出价，tokens÷1M×单价再相加。

Q4. 缓存命中率为什么重要？ > 缓存命中的输入价格是未命中的约 1/120，长对话省钱全靠它——多轮对话把历史上下文重发，服务端认出缓存过的部分就按超低价计。所以插件专门算命中率展示，用户能直观看到”缓存帮我省了多少”。

Q5. 为什么用 jsonl 不用数据库？ > 明细是 append-only：追加写天然安全（写崩最多坏最后一行）、纯文本肉眼可查、按行读可流式处理。单机个人工具不需要并发和事务，引入 SQLite 反而增加复杂度。汇总单独存 summary.json，读报表不重放明细——事实表加汇总表的两层结构。

Q6. updater 里最得意的决策？ > “是否最新”的判定算法。直觉做法是比较本地和官方版本是否相同，但本地永远领先官方几个定制提交，会天天误报。改成 behind 计数——本地落后官方提交数为 0 即最新，同时如实显示”本地领先 N”。教训：判定指标选错，准确性无从谈起——和做监控报警是同一个道理。

Q7. 安全上做了什么？ > updater 端点能执行 git/pnpm 命令，所以只监听 loopback，信任判定看 socket 地址和 Host 头、永不信任可伪造的 X-Forwarded-For；升级前检查（脏工作区拒绝、detached HEAD 拒绝、并发互斥）；升级前记回滚锚点，失败一键回滚；merge 冲突自动 abort 恢复现场。原则：破坏性操作必须可撤销。

Q8. 什么是流式响应？为什么要透传？ > 模型回答不是一次返回的，是分块流式吐出，降低用户看到首字的等待时间。透传是因为插件的角色是”观测”不是”修改”——水表不该改变水流。改动流会造成宿主行为异常，也违背插件最小侵入原则。

Q9. 上下文占用是怎么算的？ > 每次请求的 prompt 规模（未命中+缓存命中 tokens）就是当前上下文占用快照，取最近一次记录除以模型上下文窗口（1M tokens）得百分比，再按”一条中等消息约 1500 tokens”估算还能聊几条——把抽象的上下文窗口变成用户看得懂的油表。
