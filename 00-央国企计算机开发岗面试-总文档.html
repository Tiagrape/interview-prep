一、央国企开发岗面试全景（先建立认知）

1.1 典型流程

网申 → 笔试（行测 + 专业知识）→ 专业面/技术面 → 综合面（半结构化）→ HR 面 → 体检 + 政审/背调 → 录用

有的单位把专业面和综合面合成一轮（多考官同场：一半问技术一半问综合素质）；部分单位有无领导小组讨论（群面）。

1.2 面试形式：结构化 / 半结构化

  • 结构化：所有候选人抽同样的题、同样时间、同样的评分表——像标准化考试；
  • 半结构化（最常见）：固定题 + 考官自由追问，追问多来自你的简历和前面的回答——所以简历每个词都是”自邀考点”。

1.3 和互联网面试的核心差异（策略调整依据）

维度 互联网大厂 央国企开发岗
技术占比 80%+，深挖原理和手撕代码 约 40-50%，广度 > 深度，基础概念说清即可
综合素质 几乎不问 权重很高：稳定性、价值观、团队、服从性、抗压
隐形考察 聪明、能卷 稳定、靠谱、留得住
加分认知 开源、新框架 数字化转型、信创（国产化替代）
礼仪着装 随意 正装、称呼”各位考官好”、离场致谢
反问环节 问技术栈 问培养机制、业务方向（不问薪资加班）

策略结论：技术按”每个概念 30 秒说清 + 一层追问”的标准（第三章）；项目按第四章深挖题准备；综合面按第五章逐题过；每题答案往”稳定、踏实、长期”的人设上靠。

3.1 第一行 · AI Application

Q1. RAG 是什么？ > 开卷考试：先从知识库里把相关材料翻出来，塞给大模型，要求它只照着材料回答。因为大模型不知道企业自己的数据，硬答会编。我在神农和中青旅都做过，优化过”翻错书”的各种毛病。 > 追问下限：检索用向量搜索+按条件过滤；生成时强约束”无依据就明说”。

Q2. Agent 是什么？ > 让 AI 不只动嘴还能动手干活的系统：模型决定调什么工具、填什么参数，系统真去执行再把结果喂回来。比如查实时门票库存这种事，模型自己不知道，就得调工具。 > 追问下限：我们用 LangGraph 把流程拆成节点编排，而不是让模型自由发挥。

Q3. 大模型的原理？为什么会有幻觉？ > 它在海量文本上训练”预测下一个词”，学会的是语言的统计规律——所以生成很流畅，但不知道的东西它没有”我不会”的机制，会一本正经地编。工程上用 RAG 给它供真实数据、用约束压住它别乱说。 > 追问下限：幻觉只能压制不能根除——检索给依据、提示词强约束、输出带出处可核查。

Q4. Prompt Engineering 是什么？ > 写好给模型的指令的技术。四要素：角色、任务、约束、输出格式（配示例）。最关键是约束——“只准依据给定材料回答，无依据则明说”是压幻觉的核心。 > 追问下限：改提示词必须过回归评测，防止修好一个坏三个。

Q5. Tool Calling 是什么？ > 模型输出一个结构化的”工具调用指令”（比如 查库存(景区=X, 日期=Y)），系统执行后把结果喂回模型。常见错误是参数填错——日期格式不对、ID 填错，解法是工具说明里写清参数格式。 > 追问下限：它返回的是可执行的指令不是聊天文本。

Q6. LangGraph 是什么？ > 一个把 AI 流程写成”流程图”的 Python 框架。理解成医院：分诊台（识别问题类型）→ 按病情分流 → 各科室干活（检索/调工具/生成答案）→ 病历本（状态对象）全程传递数据。可以理解为”用白盒方式构建 Agent”——整体流程由代码写死，个别环节允许模型自主。 > 追问下限：比黑盒 Agent 强在流程可控：强制先检索再生成、每步能打日志、出错能定位到节点。

Q7. Query Rewrite 是什么？ > 检索前先把口语问题改写成好检索的标准问——游客问”那学生呢”，先补全成”学生门票优惠政策”再去搜。不改写的话，指代不清、口语词根本搜不到东西。 > 追问下限：神农平台的第一个节点就是干这个的。

Q8. Metadata 是什么？ > “关于数据的数据”——数据本身之外那层结构化小标签。就像图书馆的编目卡片：找书不是通读全馆的书，而是先按分类号锁书架再翻。我们用在两处：①文档块打上景区 ID、生效时间等标签，检索先按标签过滤再语义搜索（“当前生效”这种精确条件靠语义搜索表达不了）；②指标词典——别名到标准指标到物理字段的三层映射表。一句话：大模型擅长”意思相近”、不擅长”精确相等”，Metadata 就是给它配的精确锚点。 > 追问下限：什么字段值得打标签——会被拿来过滤和统计的才打。

Q9. Metadata Filter 和 Rerank 分别解决什么？ > Filter 解决”范围”：先锁对本景区、当前生效的文档再搜——结构化条件，一个等号搞定。Rerank 解决”排序”：先粗召回 50 条，再用更精细的模型慢而准地挑出最好的 5 条——海选加复审。 > 追问下限：为什么不全部精挑——精挑每条几十毫秒，只能用在漏斗末端。

Q10. Text-to-SQL 难在哪？ > 就是让 AI 当翻译官：领导说人话，数据库只懂 SQL。三种典型翻车：把”回款额”翻译成”合同额”（听岔词）、漏翻”华东区、Q2”（漏条件，数字能查出来但口径是错的，最危险）、编造不存在的字段（瞎编，好在会当场报错）。 > 追问下限：解法是三段式——先查词典、列提纲、按提纲写，最后过”安检”。

Q11. AST 校验是什么？ > 生成的 SQL 过一遍”安检机”：把 SQL 解析成结构化的语法树（用 sqlglot），核对里面的表和字段是不是真的存在、必要条件带没带。不合格打回重写，再不行就降级用固定模板——保证返回的东西至少能跑。 > 追问下限：为什么需要——语法正确不等于表和字段真实存在。

Q12. Badcase 和回归评测是什么？ > Badcase 就是线上答错的案例。回归评测 = 错题本 + 模拟卷：错误按病因分类收进固定的题集，每次改系统（检索/提示词/工具配置）都先全量重考一遍，分数不退步才准上线——防止修好一个毛病带出三个新毛病。 > 追问下限：四类错误——没知识（库里没有）、过期政策（旧文档没清）、工具参数错、没依据硬编。

3.2 第二行 · Backend（Python、FastAPI 等；⚠java/SpringBoot 建议删）

Q13. 进程和线程的区别？（2026-09-28 面试被问，必背） > 大白话：进程是车间，线程是车间里的工人。开一个车间（进程）要有独立的厂房和仓库（独立内存空间），成本高；车间里加一个工人（线程）不用新建厂房，大家共用车间里的设备和原料（共享内存），成本低。工人们共用东西所以配合快，但也会抢设备（要加锁）；车间和车间天然隔离，要传东西得走传料通道（管道/消息队列/Socket 这些 IPC 手段）。 > 技术版：进程是资源分配的基本单位，线程是 CPU 调度的基本单位。一个进程可以含多个线程；线程共享进程的堆和方法区（全局变量、对象都在一起），各自私有栈和程序计数器。进程隔离性强但创建/切换开销大；线程轻量、切换快，代价是共享带来竞态问题，需要锁或原子操作保护。 > 追问下限：①为什么线程切换比进程快——不用切页表、不刷 TLB，只换寄存器和栈指针；②一个线程崩了会把整个进程带崩（未捕获异常终止进程），进程之间则互不影响——这也是服务按进程隔离部署的一个理由。

Q14. 什么时候用多线程、什么时候用多进程？线程数怎么定？（2026-09-28 面试被问） > 先分任务类型，再定方案。CPU 密集型（纯计算，比如数据预处理、模型推理前处理）：线程多了反而互相抢核，线程数经验值 = CPU 核数或核数+1；Python 还受 GIL 限制（下一题细说），真并行要用多进程。IO 密集型（大部分时间在等网络/磁盘，比如巡检扫设备、调接口）：线程在等的时候 CPU 是闲的，线程数可以远大于核数，经验从 2×核数起步，压测调优。我们巡检就是典型 IO 密集——每台设备都要查状态走网络，所以 10 个 worker 并行收益直接。 > 追问下限：怎么验证线程数合理——压测看吞吐和延迟曲线，找”由陡变平”的拐点，跟定心跳阈值是同一个方法论。

Q15. Python 的 GIL？ > 全局解释器锁：Python 同一个进程里同一时刻只允许一个线程真正执行代码——所以多线程加速不了纯计算，计算密集要用多进程；但等待网络这类 I/O 场景多线程/异步没问题，我们的模型调用正是 I/O 密集。 > 追问下限：CPU 密集任务混进异步服务会卡死整个事件循环——丢进程池跑。

Q16. 装饰器和类型注解是什么？ > @app.post("/ask") 那种 @ 写法是装饰器：Python 里它在程序加载时就真的执行了，把你的函数登记进路由表——类似 Java Spring 的注解，但 Java 注解是被动标签要框架扫描，Python 装饰器是主动执行的代码。question: str 那个叫类型注解，本来只是备注，但 FastAPI 拿它实现了自动参数校验。 > 追问下限：装饰器一句话——“接收函数、返回函数的函数，不改函数本体给它附加功能”。

Q17. FastAPI 的开发模式是怎么回事？ > 我按它的格式写（装饰器登记 + 参数标注），给出业务逻辑代码；它负责整个流程——接请求、找到我的函数、校验参数、调用我的逻辑、把结果转成响应发回去。登记一次，之后全自动。这叫控制反转：普通脚本是代码驱动自己，框架是它驱动你的代码。 > 追问下限：函数内部的业务逻辑（检索、调模型）还是我写的，框架只负责”什么时候调用和进出转换”。

Q18. FastAPI、Starlette、Uvicorn 什么关系？ > 客服中心三层：Uvicorn 是接线员（服务器进程，守着端口接网络请求——没有它外界根本碰不到我的代码）；Starlette 是前台（把请求整理成标准单据、按地址分派给对应函数）；FastAPI 是坐席办公系统（让我写得舒服：路由写法、参数自动校验、自动文档）。日常我只跟 FastAPI 打交道，另两个装一次就不管了。 > 追问下限：ASGI 是异步服务器网关接口标准（对应同步时代的 WSGI）；为什么不用 Flask——Flask 同步，模型调用等几秒会把吞吐拖死。

Q19. RESTful API 是什么？ > 一套约定俗成的接口设计风格（不是技术）。三条规矩：地址表示东西（名词），HTTP 动词表示操作（GET 查 / POST 建 / PUT 改 / DELETE 删），无状态（服务器不记你是谁，每个请求自带全部信息，方便随时加机器扩容）。比如 GET /farms/42 就是”查 42 号田块”。 > 追问下限：状态码 200/404/400/429/500；“无状态怎么记住登录”→ 靠 token，凭证随每次请求自带。

⚠ java/SpringBoot：无出处支撑、与人设不搭，建议删除；若目标岗 JD 明确要 Java，改”了解 Java 基础”并补三天八股（HashMap 结构 / JVM 三大区域 / IOC 概念——IOC 就是 Q17 说的控制反转，Spring 靠它成名）。

3.3 第三行 · Retrieval & Data（SQL、Milvus、jieba、Redis、MQ）

Q20. SQL 手写（必须裸写）：

SELECT s.scenic_name, SUM(f.amount) AS total_income
FROM fact_finance f JOIN dim_scenic s ON f.scenic_id = s.id
WHERE f.year = 2026 AND f.quarter = 'Q2'
GROUP BY s.scenic_name ORDER BY total_income DESC;

追问下限：left join 保左表全量；where 过滤行、having 过滤聚合结果；索引像书的目录，避免一页页翻全表。

Q21. 事务 ACID？ > 四个保证：原子（一组操作要么全做成要么当没发生）、一致（数据从一个合理状态到另一个合理状态）、隔离（同时进行的操作互不捣乱）、持久（确认保存了就丢不了）。MySQL 默认隔离级别”可重复读”。 > 追问下限：并发三毛病——脏读、不可重复读、幻读，级别逐级解决。

Q22. 向量检索和关键词检索的区别？ > 向量认”意思”（问”优惠”能搜到写着”减免”的文档），关键词认”字面”（“戊唑醇”这种专业词一字不差才命中）。农业术语和冷门知识向量算不准，所以两个一起用，结果按排名融合（RRF——只用排名不用分数，因为两把刀的分数量纲不一样）。 > 追问下限：混合检索正是我们神农项目的做法。

Q23. Milvus 是什么？HNSW 是什么？ > Milvus 是向量数据库——专存”语义坐标”、回答”谁离我的问题最近”。HNSW 是它里面的索引结构（不是检索方式本身——检索是找最近，HNSW 是让找得快）：把向量组织成多层图，上层像高速公路快速逼近，底层像乡道精确到位，最终答案从最底层（全员层）的小范围精搜里出。牺牲一点准确率（95%+）换毫秒级速度。 > 追问下限：为什么近似可接受——top20 里漏一两条，整体问答无感；库百万级以内选 HNSW（吃内存换速度），亿级内存紧换 IVF（聚类分桶）。

Q24. jieba 干嘛的？为什么要灌自定义词典？ > 中文没空格，得先切成词（“小麦条锈病防治”→小麦/条锈病/防治）。jieba 用的是通用词典，不认识农业术语，会把”条锈病”切成”条/锈/病”——词被切碎等于不存在，关键词检索通道直接失效。所以我们整理农业词表（病名、药名、生育期术语），一行 load_userdict 灌进去，保证专业词整体切分。 > 追问下限：词表来源——领域资料 + 用户提问日志里挖高频词，越用越全。

Q25. Redis 是什么？ > 用内存存数据的键值数据库——内存比磁盘快十万倍，单机每秒 10 万+ 次读写。但它不只是快，还自带”自动化工具”：TTL（key 到期自动删——心跳 key 设 3 分钟，设备活着就一直续命，死了自动消失）、ZSet（按分数排序取——延迟队列：分数填到期时间，到点一把取出）、SETNX（原子占位——同一个位置只允许一个人占住，做幂等锁）。我们项目这四个用法全用上了。 > 追问下限：单线程为什么快（内存+epoll+免锁）；持久化 RDB 快照/AOF 日志，我们存的心跳数据可重建、对持久化不敏感。

Q26. 消息队列是什么？ > 两个程序之间的”传达室”：发消息的写张便条投进信箱就走（不用等谁来取），取消息的有空了来取，便条在信箱排队、不丢。解决三件事：解耦（发件人不用认识所有取件人，新订阅方零改动）、异步（投完就走，主流程不被拖慢）、削峰（一波消息涌进来先排队，下游按自己节奏取）。 > 追问下限：消息可能重复（处理完没来得及确认，传达室又发一份）→ 消费端必须幂等；延迟消息（指定 10 分钟后才能取）是”延迟确认”的实现载体。

Q27. 消息队列的消息是按顺序还是谁能取谁的？ > 两层：按”信箱”（主题 Topic）归类，取件人订阅信箱——不是每条消息写收件人，是人守着信箱。一个信箱两种玩法：多人抢着取（每条只给一个人——我们的巡检任务，100 个任务 10 个 worker 抢）或每家发一份拷贝（发布订阅——恢复事件，工单系统和分析组各拿一份）。信箱内先投先取，但多人同取或多分区时全局顺序不保证——需要严格顺序就按设备 ID 分格（同一设备的消息永远进同一格），我们工单闭环还用”执行前二次校验”兜住乱序。 > 追问下限：这就是为什么二次校验以数据库当前状态为准、不信消息顺序。

3.4 第四行 · ML

Q28. Transformer 的自注意力？ > 序列里每个时间点给其他时间点打”重要分”、按分数加权综合——“谁对我最重要”模型自己学。我们的场景：生育期序列里灌浆期权重自动升高，符合农学规律。 > 追问下限：注意力本身不识先后，要加位置编码——我们注入的是生育期阶段标记。

Q29. 为什么用 Transformer 不用 LSTM？ > LSTM 像逐字读文章，读到最后忘了开头（长序列前忘后），而且必须一个接一个算、没法并行；Transformer 全局直接建立联系 + 可并行训练。小麦生长季是典型的”长序列、关键期稀疏”结构，正适合。 > 追问下限：LSTM 靠门控（遗忘门/输入门/输出门）决定记什么忘什么，能说出即可。

Q30. GAT 和 GCN 区别？ > 都是图神经网络：节点=田块、边=地理邻近。GCN 对邻居”一视同仁”（权重按连接数固定）；GAT 让模型自己学”听哪个邻居的、听几分”——地里邻居影响本来就不均等，GAT 合适。 > 追问下限：GAT 流程——两节点特征打分、归一化成权重、加权聚合邻居信息，多头（几套独立打分）增强稳定。

Q31. 什么是过拟合？怎么防？ > 死记硬背训练数据、没学到规律——训练集上很好、新数据上拉胯。防法：早停（验证集不再变好就收手）、Dropout（训练时随机关掉一些神经元防死记）、控制模型规模、正确的数据划分（我们按年份留出——同年地块相关，随机划分会”泄题”）。 > 追问下限：为什么按年份不随机——就是防数据泄露。

Q32. 训练一个模型的完整流程？ > 数据对齐清洗 → 按年份划分 → 模型猜答案 → 损失函数打分”错多少” → 算出每个参数该往哪调（梯度）→ 小步调整 → 循环几百轮 → 验证集不再变好就停。 > 追问下限：学习率是步长——太大来回震荡不收敛，太小学得太慢。

Q33. 扰动归因和 IG 是一回事吗？（高频陷阱题） > 不是，是归因的三个家族：扰动是黑盒试错派（遮住某个输入看预测变多少，变化大=重要——像判断菜里哪种调料重要，每次少放一种尝味道）；IG 是白盒求导派（从基线到输入一路累加敏感度，解决”咸到头再加盐没感觉”的单点失灵问题）；SHAP 是博弈论分账派。我们选扰动：语义贴合”遮某段时期”、实现简单、特征少成本付得起。 > 追问下限：扰动法的坑——特征相关时会低估（成组扰动缓解）；IG 的坑——基线怎么选很敏感。

Q34. Git 的 merge 和 rebase 区别？ > merge 把两条分支拧成一股（保留分叉历史）；rebase 把你的提交搬到最新代码后面（历史一条直线更干净，但改写了历史）。工作流：开分支开发、合并前提 PR 让 mentor 审查。 > 追问下限：冲突怎么解——两人改了同一行，工具标出来人工选择保留哪边。

Q35. Linux 排查一个线上报错的过程？ > 场景化答：先 grep 'ERROR' app.log 定位报错时间点，再 tail -f 盯实时输出看复现，ps 看进程状态。比背 20 个命令有效。 > 追问下限：grep -C 3 带上下文三行；tail -n 200 看最近两百行。

Q36. Trace 排障是什么？ > 给每个请求发一个”编号”，它跨服务流转的每一步都记着这个号——排障时把一台设备的完整轨迹串成时间线。我在美团查误报就是拉一台设备的轨迹，把”判离线的时刻”和”最后心跳时刻”对齐，发现只差一个心跳周期——根因就出来了。 > 追问下限：和看日志的区别——日志是散的，Trace 串成线。

Q37. 接口联调是什么？ > 前后端（或多个系统）把接口对接调通：对字段名和格式、处理边界情况（参数没传、类型不对）。常用 Postman 手工调接口。经验：接口文档先行，联调能省一半时间。 > 追问下限：最常见的锅——两边对字段的理解不同步，所以要文档加评审。

4.1 美团 · 充电宝设备运营与异常治理平台（详版：01）

简历原文（北京三快在线科技有限公司 · 后端研发实习生 · 2026.06-2026.09）：

  • 总述：负责充电宝运营侧设备异常治理与巡检能力建设，围绕弱网场景下设备离线误报、异常工单无法及时闭环以及人工巡检成本较高等问题，参与存量业务规则优化及运营工具建设。
  • ① 设备异常误报治理：基于线上心跳Trace与设备事件日志排查弱网场景下状态频繁翻转问题，定位单次心跳超时即判离线导致的误报；参与将判定逻辑调整为连续失联窗口+恢复防抖，并通过历史事件回放验证阈值，最终同设备重复异常下降58%，离线误报率降低约21%。
  • ② 异常工单自动闭环：针对设备恢复后异常工单长期停留在待处理状态的问题，梳理设备状态事件→异常状态→工单状态流转关系，补充恢复事件监听、延迟确认与二次状态校验逻辑，使约46%的设备异常可自动完成闭环，减少人工确认操作。
  • ③ DeviceOps自动巡检：参与设备异常巡检任务开发，将长时间无心跳、状态不一致等人工排查规则沉淀为可执行巡检规则，并实现分片扫描、失败重试与结果记录；单轮巡检由约2小时缩短至20分钟以内，人工巡检工作量下降约40%。

Q1. 介绍一下这个项目？ > 平台负责全国充电宝机柜的监控、异常处理和巡检。机柜在商场餐厅走 4G 弱网，必须在线才能支持扫码借还。服务部署在公司的 Linux 服务器集群上、Docker 容器化发布。我参与三块工作：弱网误报治理（同设备重复异常降 58%）、异常工单自动闭环（46% 不用人工处理了）、人工巡检自动化（单轮 2 小时缩到 20 分钟以内）。

Q2. 心跳是什么？为什么会误报？ > 心跳是设备每 30 秒发一次的”我还活着”小包。地下室信号差，偶尔丢一两个包很正常，但旧逻辑是丢一个就判”离线”——把正常当异常，报警响个不停，运维白跑。

Q3. 防抖怎么做的？参数怎么定的？ > 两个方向都防抖：判离线要连续 3 个周期没消息（约 90 秒），不是丢一个就算；恢复后要稳定 5 分钟才算真回来（像退烧要观察一天不反复才算好）。参数不是拍的——拿历史日志回放，把窗口从 2 试到 10，画”误报率 vs 发现变慢”的权衡曲线选拐点。

Q4. 重复异常下降 58% 怎么统计的？ > 分子分母是治理前后”每台故障设备平均产生的异常条数”。核心改动是离线期间状态抖动不再重复记异常——一次故障只记一条，以前能记三五条。

Q5. 为什么不用机器学习做异常检测？ > 设备行为很简单（有心跳/没心跳），规则够用；规则可解释可回放，误报了能讲清原因，模型是黑盒没法向运营解释；误报直接产生人力成本，需要的是随时可调的机制不是要重训练的模型。要做”故障预测”那种复杂目标才值得上模型。

Q6. 工单闭环三步各防什么坑？ > 像请假销假：①监听恢复事件=装门铃，设备自愈有人知道（以前没人通知，僵尸工单堆积）；②延迟确认=观察 10 分钟再办，防止”假恢复”（弱网下冒个头又消失很常见）；③二次校验=办手续前再打电话确认——查一下设备当前真在线、工单没被同事领走，都确认才关单，防误关。

Q7. 为什么只有 46% 自动闭环？ > 剩下的 54% 是真异常：硬件坏了、断电没人管、设备被挪走，必须人上门。自动闭环的定位是消化”自己能好的”那部分，不追求 100%——硬提比例只会引入误关风险。

Q8. 分片怎么保证不重不漏？ > 按设备 ID 除以 100 取余数分 100 片——规则是固定公式，每台设备永远属于唯一一片，所有片合起来正好是全部设备，数学上保证不重不漏。10 个工人并行取任务，谁快谁多干。

Q9. 任务跑到一半挂了怎么办？ > 每处理完一台记一次进度（checkpoint），重试从断点继续不用从头来。就算整片重跑也没事——结果写入有去重键，同一台设备不会重复告警，幂等让重跑变成安全操作。

Q10. 这段实习最大的困难？ > 定阈值没有标准答案。“连续 N 个周期没心跳才判离线”听着是一行代码的事，但 N 取多少？两边都是代价：N 取大，误报少了，但真故障被发现得越来越晚；N 取小，发现快了，误报又回来了——没有两全的答案。我的做法是拿历史心跳日志做回放：把 N 从 2 到 10 逐个试，每个 N 都算出一组”误报率”和”平均发现延迟”，画成一条曲线。曲线前段很陡——N 从 2 到 3，误报率大幅下降；后面越走越平——再加大 N，误报率几乎不降了，延迟却一直在涨。那个”由陡变平”的位置就是拐点，N=3 就选在拐点上：用最小的发现延迟代价，换到了绝大部分的误报改善。这件事让我真正理解了什么叫数据驱动决策——不是找到完美答案，而是在两难里用数据找到性价比最高的那个点。

Q11. 犯过什么错？ > 巡检任务第一版我设计了”失败就整个重跑”，但没想过重跑的后果。联调时扫到第 60 台数据库卡了一下、任务失败，系统自动重跑——重跑是从头扫的，前面扫过的设备里命中过规则的又被记了一遍告警，同一台设备同一个问题，运营看到两条一模一样的告警，测试同学发现的。修复两刀：①给结果表加唯一键——同一台设备+同一条规则+同一个时间窗只允许存一条，重跑再插入同样的记录数据库直接拒绝，从此重跑多少遍都只记第一次（这就是幂等：做一次和做一百次效果一样）；②顺手把重跑改成从断的地方继续扫，连重复扫描都省了。教训：只要系统里有”重试”这个动作，就必须先问一句——重跑一遍，之前做过的事会不会再做一遍？

Q12. 项目里有没有用多线程？怎么用的？（2026-09-28 面试原题） > 有，最典型的是自动巡检任务。原来人工加脚本扫一轮约 2 小时，我们把巡检做成了多线程并行，三步：第一步分片——全部设备按设备 ID 对 100 取模分成 100 片，放进任务队列；第二步线程池领活——起 10 个 worker 线程，每个线程循环从队列领一片、扫完再领下一片，谁快谁多干，自动负载均衡，不会出现一个线程忙死一个闲死；第三步兜底——失败重试、每处理完一台记进度（断点续扫）、结果写入带唯一键（重跑不产生重复告警）。上线后单轮从 2 小时缩到 20 分钟以内。 > 追问下限：Java 里就是 ThreadPoolExecutor + 阻塞队列；我们项目用 Python 实现，思想完全一样——池化复用、队列缓冲、限流保护。

Q13. 线程是怎么划分的？怎么决定几个线程、任务怎么分？（2026-09-28 面试原题） > 一句话原则：任务类型定线程数，分片键定归属，片多于线程保均衡，幂等保安全。 > 第一步，看任务类型定线程数：巡检每台设备都要查状态、走网络等待，是 IO 密集型——线程大部分时间在等响应，所以线程数可以明显多于 CPU 核数；10 这个数是压测里从 4、8、10、16 选出来的，再往上吞吐不涨、下游接口压力反而变大。 > 第二步，数据分片”片多于线程”：100 片分给 10 个线程，故意让快的线程多领几片，自动抹平快慢差；如果 10 片给 10 个线程，一个线程卡住它那片就拖住整体。分片键用设备 ID 取模，同一台设备永远落在同一片——一个设备只被一个线程处理，天然没有共享写冲突，基本不需要加锁，这是整个设计里最关键的一步。 > 第三步，兜底三件套：结果唯一键（幂等，重试重跑安全）、断点续扫（挂了从断点继续）、失败重试有上限（防毒丸任务无限循环）。

Q14. 服务部署在什么系统上？Linux 还是 Windows？（2026-09-28 面试原题） > Linux。公司后端服务全部跑在 Linux 服务器上，容器化部署——代码提交后由 CI 流水线自动构建 Docker 镜像并发布到测试和线上环境，我这边主要负责业务代码开发，部署环节由团队标准化的发布平台完成。日常排查问题全靠 Linux 命令：grep 从日志里捞报错、tail -f 盯实时输出、ps/top 看进程和资源占用。 > 为什么服务器用 Linux 不用 Windows，三句话：①稳定省资源，服务器 7×24 跑一年不重启是常态；②一切可脚本化，运维动作都能写成命令和脚本做自动化；③生态原生——Nginx、MySQL、Redis、消息队列这些后端组件都是为 Linux 而生。 > 追问下限： > - “本地开发用什么系统？”→ 本地 Mac/Windows 都行，代码在本地写，但线上服务跑在 Linux 容器里、和部署环境一致——“我电脑上能跑”不算数，容器里能跑才算。 > - “Docker 是什么（若被问到）？”→ 把应用连同依赖打包成镜像、到哪都一致运行，解决”在我电脑上明明能跑”；容器互相隔离，一台机器按需跑多个服务实例。诚实边界：我不亲手执行 docker 命令、也没独立写过 Dockerfile，部署是团队 CI / 发布平台负责的——只讲概念、不往“我搭建 / 运维容器”方向延伸，被追问到此为止。

Q15. 用的什么语言写？为什么不是 Java？（部署题的必然追问） > 我们这条业务线的栈是 Python——服务用 FastAPI，巡检任务也是 Python 写的。团队里 Java 居多，但公司内部语言不设限，数据、脚本、AI 相关的场景 Python 是主流，我负责的部分就是 Python 实现的。Java 我有基础：课程学过、也自学过 SpringBoot，为了保持手感，我还专门用 Java 把巡检的分片逻辑重写了一遍——线程池、分片、幂等这套思想完全一样，差异只在语法和生态。如果岗位需要 Java，我上手会很快。 > 追问下限：①Java 线程池怎么写→ ThreadPoolExecutor 三个关键参数：核心线程数、队列容量、拒绝策略；②Python 和 Java 什么区别→ 动态 vs 静态类型、GIL vs 真多线程、FastAPI 轻量 vs Spring 全家桶，思想相通换语法不换思想。 > 红线：别说”项目用了 Java”——被追问 Maven/Spring/JVM 细节会露馅；诚实的口径是”Python 实现 + Java 有基础 + 已用 Java 重写过核心逻辑”。

4.2 中青旅 · Text-to-SQL / RAG / Agent（详版：02）

简历原文（中青旅控股股份有限公司(央企) · 科技创新部 · 后端/AI应用研发实习生 · 2025.06-2025.09）：

  • 总述：围绕集团经营分析与智慧文旅问答场景，开展 Text-to-SQL、RAG 检索及 Agent 工具调用链路优化，重点解决指标理解偏差、知识召回错误与生成结果可信度问题。
  • ① 经营分析Copilot：基于真实经营问数Badcase排查 Text-to-SQL 错误，定位回款额、预算完成率、应收余额等问题中的指标误映射、组织/期间解析遗漏及字段幻觉；参与将生成链路拆分为指标解析、QueryPlan与SQL构建，并增加Metadata匹配及AST校验。基于218条典型问数回归验证，SQL可执行率由76.1%提升至89.4%（+13.3pp）。
  • ② 集团指标语义治理：针对景区、酒店、旅行服务等系统存在同名指标口径不同、同义指标字段不一致的问题，参与梳理指标定义、计算口径及来源字段，建立业务别名→标准指标→物理字段的Metadata映射；对存在多口径的问题增加指标消歧与澄清机制，累计沉淀126个核心指标、247组字段及别名映射。
  • ③ 智慧文旅RAG：基于线上咨询Badcase定位跨景区串召、过期政策误召回及长文档关键条件丢失问题，在向量检索基础上增加景区ID、生效时间等MetadataFilter，并采用父子Chunk+Rerank优化政策文档召回；在326条真实咨询问题集上，Top-5知识命中率由80.4%提升至90.2%（+9.8pp）。
  • ④ AIBadcase回归评测：围绕线上问答错误建立Badcase分类，重点覆盖无知识命中、过期政策、Tool参数错误及无依据生成等问题，并构建固定回归集验证Retrieval、Prompt与ToolCalling改动；累计分析137条典型Badcase、完成7轮策略迭代，核心问题端到端正确率由78.6%提升至87.3%（+8.7pp）。

Q1. 介绍这段实习？ > 集团两个 AI 场景：给管理层用的”用自然语言查经营数据”（Text-to-SQL），给游客用的”智能问答政策”（RAG）。环境全部私有化部署——服务跑在集团机房的 Linux 服务器上，模型也是私有化调用，数据不出央企机房。我做了四块：问数链路优化（可执行率 76.1%→89.4%）、指标治理（126 个指标、247 组映射）、问答检索优化（Top-5 命中率 80.4%→90.2%）、以及贯穿全程的回归评测体系（端到端正确率 78.6%→87.3%）。

Q2. Text-to-SQL 三段式是什么？为什么拆？ > 以前是”一句问题直接生成 SQL”，错了不知道错在哪。拆成三段：指标解析（先查指标词典，把”回款额”锁定成唯一定义）、查询计划（列提纲，把”华东区、Q2”强制写成过滤条件）、按模板生成 SQL。三类错误各有专人拦：听岔词的词典拦、漏条件的提纲拦、编字段的最后安检拦。

Q3. 可执行率和正确率是一回事吗？（最常考） > 不是。可执行率 = SQL 能跑通不报错的比例；正确率 = 口径也对。最阴险的是漏了过滤条件的 SQL——照样能跑出数字，看着挺正常，实际查的是全公司全年。所以可执行率只是下界，我们另有人工抽检口径正确率。

Q4. 跨景区串召怎么定位、怎么解的？ > 每个回答都带”出处”标注，抽错误案例一看：召回的文档根本不是问的那个景区。根因是各景区政策文本太像（都是”XX 人群半价”就差景区名），语义搜索分不出来。解法是给文档打标签（景区 ID、生效时间），检索先按标签过滤再语义搜——一个等号解决的问题，不值得换更强的模型。

Q5. 父子 Chunk 为什么有效？ > 检索和生成对文本块的要求相反：检索要小块（语义集中搜得准），生成要大块（上下文完整不被断章取义——“仅限学生”和”半价”不能被切开）。父子结构解耦两者：小块拿来搜，命中后换成它所属的大块喂给模型。

Q6. Rerank 用的什么？ > bge-reranker。流程是海选加复审：向量搜索先快而粗地捞 50 条，精排模型慢而准地逐条细读挑出 5 条。代价是每条几十毫秒，但答案错误的代价（游客投诉、口径事故）远大于这点延迟。

Q7. 指标治理为什么是地基？ > 集团各系统黑话不统一：同一个东西 N 种叫法（入园人数/客流量/接待人次），同一个叫法 N 种含义（各家的”营收”口径不同）。翻译 AI 被这个害惨。我们编官方词典：各种叫法→标准名（带精确定义和口径）→仓库里的真实字段。126 个指标 247 组映射。AI 应用的上限取决于数据治理，不取决于模型——这是这段实习最大的认知。

Q8. 多口径指标怎么消歧？ > 解析置信度高就用默认口径，但答案里显式标注”按含税口径”；置信度低就反问用户，给选项不让开放填——宁可多问一句，不可猜错口径，错数字进了汇报材料是事故。

Q9. 回归集怎么用？ > 把错误案例和典型好题固化成一套不变的考卷。每次改检索、改提示词、改工具配置，先全量重考，各项正确率不许退步才上线。AI 系统改动的后果不可预测——教会它”没依据别乱答”，它可能变得过度保守；没有固定考卷，这种悄悄退步根本发现不了。7 轮迭代就是 7 次这个循环。

Q10. 这段最大的困难？ > 归因。同一个错误答案，检索、生成、工具五个环节都可能背锅。一开始只看结果就动手改，方向错过一次（以为要修提示词，实际那批题根本没检索到材料）。后来养成逐环节留痕：把检索结果、给模型的提示词、工具参数都打出来，先定位错在哪环再动手。

Q11. 为什么不微调一个模型？ > 三原因：标注数据只有百级，微调要千级以上；微调贵且慢，业务口径还在变；链路工程可解释可干预——出问题能定位到环节，微调是黑盒。而且基础模型一直在换代，链路方案换个模型能直接用。

Q12. 部署在什么环境上？（部署环境题，和美团那题对照着记） > 全私有化：FastAPI 服务用 Uvicorn 跑在集团机房的 Linux 服务器上，Embedding 和 Rerank 模型也都是私有化部署、内部调用。这是央企的硬约束——数据不能出机房，所以选型时”可私有化”是一票否决级别的标准（选 bge 系列除了中文效果好，能私有化部署是前提）。 > 追问下限：“和美团的环境有什么区别？”→ 美团是互联网基建，CI/CD + 容器编排很成熟，发布是流水线一键的；央企私有化环境更朴素，就是 Linux 服务器直接跑服务，更看重稳定和合规——两段实习正好把”先进基建”和”朴素环境”都见过了。

4.3 神农 · 大模型平台（详版：03 待写）

简历原文（神农大模型平台 · 北京市农林科学院 · 2025.02-2025.08）：

  • 技术栈：Python、FastAPI、Starlette、Uvicorn、LangGraph、Milvus、jieba、asyncio、anyio
  • 项目描述：参与农业领域大模型应用平台开发，面向农业知识问答、智慧种植、病虫害分析、遥感气象等场景，结合农业知识库与大语言模型构建智能问答及任务处理能力；本人主要负责后端AI应用相关功能开发。
  • ① 农业知识检索：参与RAG问答链路开发，对农业教材、科研资料及种植技术文档进行清洗、切分和向量化，基于jieba+Milvus完成关键词与向量检索，将召回知识片段注入Prompt，改善农业专业术语及长尾知识的检索效果。
  • ② Agent流程编排：基于LangGraph将Query处理、知识检索、模型调用和工具执行等步骤拆分为独立节点，通过状态对象维护会话上下文和中间结果，并根据不同农业场景组合执行流程，降低复杂问答链路的耦合度。
  • ③ 异步模型服务：基于FastAPI+Starlette+Uvicorn搭建AI服务接口，使用asyncio/anyio处理模型调用、向量检索等I/O密集型任务，并通过CapacityLimiter控制模型调用并发，避免瞬时请求造成服务拥塞。

Q1. 介绍这个项目？ > 农林科学院的农业大模型平台，四个场景：知识问答、智慧种植、病虫害分析、遥感气象。我负责后端 AI 应用开发：知识检索链路、AI 流程编排、异步服务接口。定位是从零搭建（0→1），这段让我把 RAG 和 Agent 从”会调 API”打到”知道每层为什么这么设计”。

Q2. 为什么要混合检索？ > 农业专业术语（条锈病、戊唑醇）和冷门病害，向量模型训练时见得少，算”语义坐标”不准；关键词检索恰好相反——专业词一字不差精确命中，但”打什么药”搜不到写着”防治用药”的文档。两个各补各的短板，结果按排名融合。

Q3. jieba 自定义词典做了什么？ > “小麦条锈病”默认会被切成”小麦/条/锈/病”——词碎了等于不存在，关键词检索通道失效。我们把农业词表（病名、药名、生育期术语）灌进 jieba，保证专业词整体切分。词表从领域资料和用户提问日志里持续补充。

Q4. 向量库为什么选 HNSW 索引？ > HNSW 是多层图结构，上层像高速公路快速逼近目标、底层精确到位，毫秒级出结果，代价是吃内存。我们的库百万级以内、内存扛得住，选它拿低延迟高召回；如果上亿条向量内存紧张，会换 IVF（聚类分桶）那类省内存的方案。

Q5. Agent 编排讲一下？ > 像医院：分诊台先识别问题类型（病虫害还是知识问答，顺便把口语改写成标准问）→ 按类型分流 → 各科室干活（查知识库、调天气工具、生成答案）→ 病历本（状态对象）全程传递，每步结果都记在上面。好处：每步只干一件事、出错翻开病历本就知道哪步错、加新场景加节点就行不动老代码。

Q6. 为什么用 LangGraph 不用黑盒 Agent？ > 黑盒 Agent 是模型自己决定下一步干什么、循环到它觉得完——流程不受控，可能跳过检索直接生成。LangGraph 是显式的图，先走哪步、什么条件走哪条路全写在代码里：强制先检索再生成、每步可打日志可单测。生产系统要确定性。

Q7. 为什么服务要做成异步？ > 调一次模型要等好几秒，这段是纯等待不是计算——同步模式下程序干等着，别的请求全堵着。异步像烧水泡茶：点上火转身去拿茶叶，水开了回来冲——单线程同时照看几十个请求，等待时间被利用起来了。

Q8. CapacityLimiter 是干嘛的？ > 给模型调用装”景区限流”：最多 10 个请求同时调模型，其他的排队，完成一个放行一个——防止瞬时洪峰把下游推理服务打爆。上限数字靠压测：并发逐步加大，看下游延迟和错误率在哪拐弯，取拐弯前留余量。

Q9. 泛化性怎么样？ > 跨区域会掉点——气候、品种、种植制度不同。诚实讲这是论文里也讨论的局限，跨区需要局部微调。讨论局限是科研素养，回避才是心虚。
