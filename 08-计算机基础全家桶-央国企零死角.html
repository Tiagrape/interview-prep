一、MySQL 深入

1.1 ★ 索引是什么、为什么快（B+ 树）

类比：书的目录。没有目录找一段内容要一页页翻（全表扫描）；有目录先定位页码直接翻到。 为什么用 B+ 树这种结构（追问必到）：B+ 树是”矮胖的多叉树”——每个节点不是二叉的俩孩子，而是一页装很多键（像目录的一级章/二级节），树矮意味着从根到叶只跳 3-4 次（每次跳 = 一次磁盘读，磁盘读是大头，跳的次数少 = 快）；且叶子节点之间有链子串起来——范围查询（查 3 月到 5 月的所有订单）顺着链子扫一遍就行。

30 秒答案：索引是把某几列预先排好序的查找结构，MySQL InnoDB 用 B+ 树——矮胖多叉减少磁盘访问次数，叶子节点成链方便范围查询。没有索引 O(n) 全表扫，有索引近似 O(log n)。 追问下限：主键索引（叶子存整行数据，聚簇索引）vs 普通索引（叶子存主键，还要回表再查一次——“回表”这个词说出来就是加分）；为什么推荐自增主键——插入总是追加到最右边，不会引起页分裂。

1.2 ★ 索引什么时候失效（高频坑题)

类比：你按拼音排好了通讯录，结果有人问你”名字里带’明’的都有谁”——拼音序根本帮不上忙，只能全翻。以下操作等于”让有序白排”：

30 秒答案：六种典型失效——①对索引列用函数或运算（WHERE YEAR(date)=2026，排好的是日期不是年份）；②左模糊 LIKE '%xx'（开头是通配符，等于问”带某字的都有谁”；'xx%' 右模糊不失效）；③隐式类型转换（列是字符串却拿数字查，MySQL 悄悄给列套了函数）；④联合索引不满足最左前缀（建了 (a,b,c) 却只按 b 查——目录按 a→b→c 排，跳过 a 没法定位）；⑤ OR 连接了无索引的列；⑥ 优化器评估回表太多不如全扫（数据占比太大）。 最左前缀追问：联合索引像”省→市→区”的地址目录，必须从省开始查才能用上目录。

1.3 ★ 事务隔离级别与 MVCC（上次背了名字，这次讲原理）

先复习并发三毛病：脏读（读到别人没提交、可能反悔的数据）、不可重复读（同一事务内两次读同一行结果不同——别人改了并提交）、幻读（两次读同一范围，行数变了——别人插入了新行）。

30 秒答案：四个级别逐级解决——读未提交（三病全有）→ 读已提交（解决脏读）→ 可重复读（MySQL 默认，再解决不可重复读）→ 串行化（全解决但性能差）。 MVCC（多版本并发控制）原理——类比：每个事务开工时拍一张数据的”版本快照”，之后 reads 都看自己的照片，别人改了也不影响我——读写互不阻塞，靠”多个版本并存”实现。实现靠隐藏的两个版本列 + undo log 版本链，按隔离级别决定”照片拍多严”。

1.4 ★ 三大日志（redo / undo / binlog）

类比：一家店的三本账： - redo log（重做日志）= 存档点：先顺序记下”我改了什么”再慢慢刷盘——断电后照着存档重放，已提交的数据不丢（持久性）； - undo log（回滚日志）= Ctrl+Z：记录”改之前是什么”——事务失败或 ROLLBACK 时逆向恢复（原子性）；MVCC 的版本链也是它； - binlog（归档日志）= 流水总账：Server 层记录所有变更，给主从复制和数据恢复用——从库照着总账重放一遍就和主库一致了。

30 秒答案：redo 保证持久性（先写日志再刷盘，崩溃恢复），undo 保证原子性（回滚）并支撑 MVCC，binlog 用于主从复制和恢复。redo 是 InnoDB 引擎层的物理日志，binlog 是 Server 层的逻辑日志。

1.5 慢查询怎么排查优化（实操题，勾连简历）

30 秒答案：①开启慢查询日志找到慢 SQL；②EXPLAIN 看执行计划——重点看 type（出现 ALL 就是全表扫）、key（用没用上索引）、rows（扫了多少行）；③对症下药：加/改索引、改写 SQL（消除失效写法）、避免 SELECT *、大分页用”游标式”（WHERE id > 上次末尾 代替 LIMIT 100000, 10——跳过 10 万行是白跳的）。 勾连：“我在中青旅做 Text-to-SQL，生成的 SQL 都要过 AST 校验+执行计划检查，理念一样。”

二、Redis 深入

2.1 ★★ 缓存三兄弟：穿透 / 击穿 / 雪崩（必考，一个类比记住）

背景：缓存的标准姿势是”查缓存→没有→查数据库→写回缓存”。三兄弟都是请求绕过缓存砸到数据库的三种方式：

名字 是什么 类比 解法
穿透 查根本不存在的数据（缓存永远不会有） 有人反复拨一个空号，前台每次都去查号簿 ①空值也缓存（短 TTL）②布隆过滤器提前拦”肯定不存在”
击穿 某个热点 key 恰好过期，瞬间全部请求砸库 商场最火的店恰好盘点歇业，人群冲进仓库 ①互斥锁：只放一个请求去重建缓存，其他等 ②热点 key 不设过期
雪崩 大批 key 同时过期（或 Redis 整个挂了） 整层楼同时关门，全部人涌向仓库 ①过期时间加随机值错峰 ②集群高可用 ③限流降级兜底

30 秒答案：穿透是查不存在的数据打穿缓存——空值缓存加布隆过滤器；击穿是单个热点 key 过期——互斥重建或热点不过期；雪崩是大批 key 同时失效——过期时间加随机、集群部署。共同思路：别让请求同时落到数据库。

2.2 ★ 缓存和数据库的一致性（高频）

类比：公告栏（缓存）和档案室（数据库）要保持一致——正确姿势：先改档案室，再把公告栏的旧公告撕掉（删除缓存），下次有人看时再贴新的（懒加载）。

30 秒答案：常用”先更新数据库，再删除缓存”（Cache Aside）。为什么是删缓存不是更新缓存——并发写时两次更新的先后可能乱，删除让下次读时自然重建，简单且不易错。为什么先库后缓存——反过来（先删缓存）在删完到更新库之间有请求会把旧值重新载入缓存。极端不一致再用延迟双删或订阅 binlog（canal）异步删。 勾连：和你美团项目”二次校验以数据库当前状态为准”是同一个原则——数据库是唯一真相源。

2.3 ★ 分布式锁（SETNX 那道的完整体）

类比：公司唯一的会议室预订系统——谁先在系统里订到（SETNX 成功）谁用，用完释放（DEL）；订不到的等或放弃。

30 秒答案：Redis 分布式锁的三个关键点——①加锁用 SET key 唯一值 NX EX 过期时间（一条原子命令同时完成”占位+设过期”）；②必须设过期时间：持锁的进程崩了没人释放，过期是唯一的自动解锁出路；③值必须唯一（请求 ID）：删锁前先比对是不是自己的锁——防止 A 的业务超时、锁已过期被 B 拿走后，A 回来误删了 B 的锁。释放锁的理想姿势是 Lua 脚本把”比对+删除”做成原子。Redisson 是成熟封装（带看门狗自动续期）。

2.4 主从复制 / 哨兵 / 集群（一句话梯队）

30 秒答案：主从复制=一主多从，写主读从、主把变更同步给从（读写分离扩读能力）；哨兵=加一个监工盯着主，主挂了自动推选从升主（自动故障转移）；集群=数据分片到多个主（每主再带从），容量和写能力水平扩展。记忆：主从管”读得多”，哨兵管”怕挂”，集群管”装不下”。

2.5 大 key / 热 key（中频）

大 key（一个 key 装了几百 MB）：删它会卡单线程（异步删 UNLINK）、拆分结构；热 key（一个 key 被打爆）：本地缓存兜一层、key 加后缀分散到多节点。

三、计算机网络

3.1 ★ OSI 七层 / TCP-IP 四层（背四层版）

类比：寄快递——你写信（应用层：内容）→ 快递单填收发件人（传输层：端口， TCP/UDP）→ 分拣中心看城市路由（网络层：IP 地址选路）→ 每段路的司机（链路层：MAC 逐跳传递）。七层版只是把其中几步再细分（表示层=统一格式加密，会话层=建立会话）。

30 秒答案：TCP/IP 四层从上到下：应用（HTTP/DNS）、传输（TCP/UDP，端口到端口）、网络（IP，主机到主机选路）、链路（相邻设备传输）。HTTP 跑在 TCP 上、DNS 是应用层的”电话簿”。

3.2 ★★ 三次握手（必考，要会画）

类比：第一次见面对暗号： 1. 客户端：“能听到吗？”（SYN） 2. 服务端：“能听到！你能听到我吗？”（SYN+ACK） 3. 客户端：“能！开始聊。”（ACK）

为什么是三次不是两次：两次的话，服务端无法确认”我能发、你能收”这条链路；且客户端一个迟到的旧连接请求（网络里迷路了半天才到）会让服务端白白建立没人用的连接——第三次握手给了客户端否决权。

3.3 ★ 四次挥手 + TIME_WAIT

类比：挂电话的礼貌告别—— 1. 客户端：“我说完了”（FIN）； 2. 服务端：“好，我知道了”（ACK）——但服务端可能还有话没说完； 3. 服务端：“我也说完了”（FIN）； 4. 客户端：“好，再见”（ACK），再等一会儿（TIME_WAIT，2 个最大生存期）才真正收线。

为什么四次：TCP 全双工（两边都能发），一方说完另一方可 能还有数据——“知道了”和”我说完了”不能合并，所以各两次。 为什么 TIME_WAIT：保证最后一个 ACK 丢了还能重发；让旧连接的残包在网络中自然死亡，不污染新连接。

3.4 ★ HTTP 各版本 / HTTPS

30 秒答案：HTTP1.0 一次连接一个请求；1.1 长连接（Keep-Alive，建一次连发多个请求）但队头堵塞（一条队前面慢了后面全等）；HTTP2 多路复用（一个连接并行跑多个请求）+ 头部压缩；HTTP3 换 UDP 底座（QUIC）解决 TCP 层队头堵塞。 HTTPS = HTTP + TLS：握手时服务器出示证书（公钥，防冒充——像注册过的官方邮箱）；之后协商对称密钥加密通信。一句话：“证书验身份，对称加密传内容”。默认端口 443（HTTP 80）。

3.5 从输入网址到看到页面（综合题，串场用）

30 秒答案：输 URL → DNS 解析域名成 IP（先查本机缓存→运营商→递归查询）→ TCP 三次握手建立连接 →（HTTPS 再加 TLS 握手）→ 发 HTTP 请求 → 服务器处理返回响应 → 浏览器解析 HTML/CSS/JS 渲染 → 四次挥手断开。这题是上面所有知识的串联，答的时候分层说清楚就是高分。

3.6 Cookie / Session / Token ★

类比：办会员的三种方式—— - Cookie：把信息存在你身上（会员卡带在身上，每次出示；不安全、容量小）； - Session：信息存在店里，只发你一个编号（报号就能查——但店只有一家，开分店〔分布式〕就麻烦了）； - Token（如 JWT）：发你一张防伪签名盖章的自包含凭证——分店验一下章就认，不用打电话回总店（无状态、天然适配分布式）。

30 秒答案：Cookie 客户端存储自动携带；Session 服务端存储靠 SessionID 关联，集群要共享存储；Token 自包含信息加签名，服务端无状态只需验签——适合分布式和前后端分离。勾连 RESTful 的无状态：“RESTful 提倡无状态，Token 正好是这个哲学的落地，我两边项目都用 token。”

四、操作系统

4.1 ★ 内存管理：虚拟内存

类比：银行授信——程序以为自己有 4GB 空间（虚拟地址），实际物理内存可能只给了正在用的几页；要用到没映射的页，银行现给现映射（缺页中断，从磁盘调入）。每个进程都有自己独立的虚拟空间——互相看不见，天然隔离（A 崩了 B 无感）。

30 秒答案：虚拟内存给每个进程一个独立、连续的假象地址空间，实际按页映射到物理内存和磁盘交换区。好处：进程隔离、程序不必关心物理布局、物理内存可以超卖（按需调页）。缺页 = 访问的页不在内存，触发从磁盘换入。 延伸一句：局部性原理（刚用过的很快再用——时间局部性；挨着的马上会用——空间局部性）是这一切划算的原因。

4.2 ★ I/O 多路复用（select/poll/epoll）

类比：餐厅传呼台——一万个桌子都可能按铃： - select/poll：服务员轮流跑一圈问每桌”按铃了吗”（每次都要全量扫一遍，桌子多了累死）； - epoll（Linux 的王牌）：装一个总呼叫器——哪桌按铃它直接亮哪桌的号，服务员只处理亮灯的（事件驱动，注册一次、就绪回调，几万连接也轻松）。

30 秒答案：I/O 多路复用 = 一个线程监视大量连接、谁就绪处理谁。epoll 高效的原因：内核维护红黑树存连接（注册一次）+ 就绪链表回调通知（不轮询全量）。勾连：“Redis 单线程快、Nginx 高并发、Python asyncio 的底层，全是 epoll——我神农项目的异步服务就是这个原理。”

4.3 零拷贝（中频，说清”省了几次搬运”）

类比：传统读文件发网络：数据从仓库→前台打包间（内核缓冲）→柜台（用户空间）→又跑回打包间（socket 缓冲）→发出，来回搬运。零拷贝 = 仓库的东西直接装车发走（sendfile：内核里直接从文件缓冲怼到网卡），省掉搬到柜台再搬回来的两趟。

4.4 用户态和内核态

类比：家里 vs 电闸房。程序平时在自己家（用户态，干普通事）；要动电闸（读磁盘、收网络包）必须去电闸房（内核态，操作系统代劳，安全但切换有开销）。系统调用 = 申请去电闸房办一件事。

4.5 进程间通信 IPC 一句话梯队

管道（父子进程的单向水管）→ 消息队列（格子信箱）→ 共享内存（同住一屋看同一块白板，最快但要自己加锁）→ 信号量（锁本身）→ Socket（跨机器也能通信——网络通信的底座）。

五、数据结构与算法

5.1 十大排序，重点背四个

排序 思路（类比） 复杂度 备注
冒泡 相邻俩人比身高，大的往后挪，一轮下来最大到尾 O(n²) 最差但必会写
快排 ★ 选个基准，比它小的站左边大的站右边，两边递归——分组站队 平均 O(n log n)，最坏 O(n²) 面试手撕 Top2，基准随机选防最坏
归并 两个已排好的队列合成一个（两叠排好的牌轮流抽小的） 稳定 O(n log n) 稳定排序的代表（相等的元素顺序不变）
堆排 用二叉堆（大顶堆堆顶永远最大）反复取顶 O(n log n) 和 TopK 是亲戚

30 秒答案：快排——选基准分区递归，平均 nlogn 最坏 n²（已有序+固定选头）；归并——分治到底再合并，稳定 nlogn 但要额外空间；堆排——建堆反复取顶，原地 nlogn 不稳定。稳定性 = 相等的元素排完序相对顺序不变——报表按多字段排序时重要（先按金额排，再按日期排，金额相同的日期顺序不乱）。

5.2 高频手撕思路（每个一句话套路）

  • 反转链表：三个指针 prev/cur/next，走一步翻一个（“改牵手的方向”）；
  • 判断环：快慢双指针（一快一慢，套圈了=有环——操场跑圈快的人追上慢的）；
  • 合并两个有序链表：双指针各指一头，每次摘小的接到结果上；
  • 二叉树遍历：前/中/后序 = 访问根的时机在前/中/后；层序 = 队列（先进先出逐层出）；
  • 两数之和：哈希表存”看过的数→下标”，来一个新数查”补数在不在”——空间换时间；
  • 二分查找：有序才能用，每次砍一半 O(log n)——注意 mid 防溢出写 left+(right-left)//2。

5.3 TopK 问题（海量数据取前 K）

30 秒答案：N 亿个数取最大前 100——维护一个 100 大小的最小堆：新数比堆顶（当前第 100 名）大就踢掉堆顶换入。全程只跟 K 个数较劲，O(n log k)，不用全排序。勾连：“RAG 检索从百万文档取 Top5 就是同一问题——向量库的 HNSW 和 Rerank 后取前 K 本质都是 TopK。”

5.4 布隆过滤器（说得出=加分）

类比：一个很大胆的门卫：他说”没见过”就一定没见过（绝不放错）；他说”见过”可能看走眼（小概率误判）。原理：一个位数组+k 个哈希函数，加元素时把 k 个位置标 1；查询时 k 个位置都是 1 才说”可能存在”。用途：缓存穿透的防火墙、爬虫 URL 去重。特点：可能误判存在、绝不漏报、不能删除。

六、消息队列深入（00 里学了基础，这里补”三连问”）

6.1 ★ 消息丢了怎么办（分三段保障）

30 秒答案：生产端——发完等确认（ack），没确认就重发；MQ 端——消息持久化到磁盘再确认（没落盘就挂了消息就没了）；消费端——处理完成再确认（手动 ACK；先确认后处理的话，处理到一半崩了消息就丢了）。三段各兜一层，配合消费端幂等（重发会导致重复）。 勾连：“这套和我在美团的’延迟确认+二次校验’是一个思路——每个环节都不轻信上一步。”

6.2 消息积压怎么办

30 秒答案：先定位原因（消费者挂了/处理变慢/流量暴增）。扩容：加消费者实例（注意分区数是消费并行上限）；批量消费提吞吐；可重算的历史消息极端时跳过或转移。勾连：美团巡检”失败分片登记下轮补扫”就是主动管理积压。

6.3 三大 MQ 选型一句话

Kafka：吞吐之王，日志流/大数据管道，顺序写+零拷贝；RocketMQ：业务消息全能选手，原生延迟消息、事务消息；RabbitMQ：路由灵活、协议友好，中小流量。（你项目的选择口径：设备事件用 RocketMQ——要延迟消息做”延迟确认”。）

七、分布式与高可用概念（入门级，答出就是降维）

7.1 CAP 定理

类比：三个愿望只能同时实现两个——网络分区（P：机器间断网）必然发生，剩下一致（C：所有机器数据时刻一致）和可用（A：每个请求都有响应）只能二选一。注册中心举例：ZooKeeper 选 CP（宁可拒绝服务也要一致）、Eureka 选 AP（宁可给旧数据也要回话）。

7.2 限流 / 熔断 / 降级（高可用三板斧，一套话记住）

类比：医院急诊在疫情高峰的三招——限流=门口发号，超过接待能力不让进（计数器/令牌桶/漏桶）；熔断=某科室连续出事直接挂牌停诊一段时间，请求不再送进去（快速失败），过段时间试探性恢复（半开）；降级=非核心服务先撤（体检预约停了），保核心（抢救照常）——返回兜底数据或友好提示。勾连：“我神农的 CapacityLimiter 就是限流思想——保护下游模型服务。”

7.3 负载均衡

30 秒答案：把请求分摊到多台机器——四层（按 IP/端口，LVS，转发快）和七层（按 HTTP 内容，Nginx，能按路径/头部路由）。策略：轮询、加权轮询、最少连接、一致性哈希（节点增减只影响相邻段——“固定去哪家奶茶店，换店长只重新分配一条街”）。

7.4 分布式 ID（中频一句话）

为什么不用自增主键——分库后各库都从 1 开始会撞。方案：UUID（无序，索引不友好）、雪花算法（时间戳+机器号+序列号拼 64 位，趋势递增——记住名字”雪花”）。
