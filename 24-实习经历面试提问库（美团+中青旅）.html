实习经历面试提问库（美团 + 中青旅）· 题+答案

只留题目和答案，答案按"可直接开口讲"的语感写，背骨架不背原文。 数据口径：美团充电宝（后端稳定性）/ 中青旅（AI 应用可信度）。

一、美团充电宝 · 设备异常治理平台（后端实习）

Q1 介绍一下美团这段实习？ A：我在美团充电宝设备运营平台做后端研发，围绕三个问题做优化：①弱网误报治理——把"丢一个心跳就判离线"改成"连续失联窗口+恢复防抖"，同设备重复异常降 58%、离线误报率降约 21%；②异常工单自动闭环——监听设备恢复事件做延迟确认和二次校验，约 46% 工单不再需要人工处理；③人工巡检规则代码化+分片并行扫描，单轮巡检从约 2 小时缩到 20 分钟以内。

Q2 你具体负责什么？哪些是 mentor 帮你的？ A：我的 mentor 是正式员工，负责整体方案设计和评审。我负责异常治理这块的具体开发和验证：防抖逻辑实现和回放脚本、闭环消费者开发、巡检分片改造。方案我先出设计文档，mentor 评审提意见后再动手，上线走团队灰度流程。

Q3 为什么要做异常治理？怎么发现该优化的？ A：设备离线直接影响借还收入，但比离线更隐蔽的是误报——每次误判都让运维白跑一趟，还让运营对报警脱敏，真异常被淹没。所以目标不是消灭报警，是提高报警的信噪比。发现它靠两个信号：运营周会反馈误报多、销单烦；数据上同设备异常条数分布有长尾（一台设备一个月几十条异常，明显不正常）。

Q4 连续失联窗口取几？阈值怎么定的？ A：心跳约 30 秒一次，窗口取连续 3 个周期（约 90 秒）。不是拍的：回放两周历史心跳日志，N 从 2 遍历到 10，N=3 相比 N=2 误报率降得最陡，再往后收益递减但检测延迟线性增加，所以选 3。真故障晚 90 秒发现可接受，因为工单处理本身是分钟到小时级。

Q5 为什么不直接用 TCP 断连判离线？ A：TCP 断连只说明连接层断了，原因可能是 NAT 超时、基站切换、弱信号，设备本身是好的、马上会重连。离线是业务概念不是连接概念，所以用应用层心跳超时来判。

Q6 "58%"的分子分母是什么？ A：分母是治理前每台故障设备在一次故障周期内平均产生的异常条数，分子是治理后的平均条数。因为离线期间的状态抖动不再重复记异常（一次故障只记一条），所以下降明显。回放对比就能算，线上数据也验证了这个量级。

Q7 防抖会让真故障发现变慢，怎么权衡？ A：明确承认 trade-off：用误报率换检测延迟。判断依据是业务容忍度——工单从生成到人工处理本身是小时级，多 90 秒检测延迟几乎无感；但一次误报是运维白跑一趟（几十分钟人力），所以方向上偏向压误报。

Q8 工单自动闭环的完整流程？ A：心跳稳定满 M 分钟 → 发 RECOVERY 事件到 MQ → 闭环消费者：①查有无"待处理"关联工单（无则结束，幂等）→ ②不立即关，丢延迟队列 10 分钟（延迟确认）→ ③到点二次校验（最后心跳是否新鲜 + 工单是否仍待处理）→ CAS 关单。三步各防一个坑：没监听=自愈无人知晓；没延迟确认=假恢复导致开了关关了开；没二次校验=旧消息当现在事实，误关运营正在处理的单。

Q9 重复消费/乱序怎么办？幂等怎么实现？ A：MQ 是 at-least-once，重复和乱序都会发生。两层防护：消费端幂等——按设备+工单+动作去重，关单用 CAS 式状态更新（WHERE status='待处理'），重复消息第二次执行影响行数为 0 自然失效；乱序靠二次校验兜底——关单执行前以当前数据库状态为准，不以消息内容为准。

Q10 延迟确认怎么实现？ A：延迟消息（MQ 的延迟级别）或 Redis ZSet 按到期时间轮询。取舍：MQ 延迟消息可靠、级别固定；ZSet 灵活但轮询有空转和宕机恢复问题。我们场景 10 分钟是固定档位，用延迟消息更简单可靠。

Q11 为什么自动闭环率只有 46%？剩下呢？ A：剩下的是真异常：硬件故障、断电无人恢复、设备被挪走，必须人工现场处理。自动闭环定位是消化"自愈型异常"，不追求 100%，强行提高比例只会引入误关风险。

Q12 分片怎么保证不重不漏？ A：device_id % 100 切 100 片，分片规则是纯函数——同一设备永远属于同一片，所有片合起来恰好等于全量，数学上保证不重不漏。任务只带片号进队列，10 个 worker 并行消费，片数大于工人数实现负载均衡和小的重试粒度。

Q13 任务跑到一半进程挂了怎么办？ A：片内每处理完一台记 checkpoint，重试从断点继续；即使整片重跑也安全，因为结果写入有去重键（设备+规则+时间窗），不会重复告警——幂等让重跑变成零成本的安全选项。

Q14 失败重试为什么带退避？ A：失败大多是暂时性故障（DB 备份、网络抖动），立刻重试等于往刚出问题的服务上再压一刀。退避（5s→15s→45s）给下游喘息时间；限 3 次是止损，3 次都不行说明是真故障，登记失败分片等补扫。

Q15 Redis 在这个系统怎么用的？ A：存设备实时状态热数据：device_id → 最后心跳时间戳/失联计数器，设 TTL 兜底（检测任务漏扫，key 过期也能触发）。追问 TTL 删除策略答惰性删除+定期删除；我们按 device_id 分散过期，不会集中过期打崩。

Q16 为什么用消息队列？ A：解耦+削峰+异步。设备状态服务和工单系统解耦，恢复/异常事件通过 MQ 传递；心跳高峰期事件量大，MQ 缓冲。追问丢失怎么办：生产端确认+持久化+消费端幂等（at-least-once+幂等≈exactly-once）。

Q17 CAS 更新是什么？为什么不用先查后改？ A：先查后改在"查"和"改"之间状态可能被别人改掉（竞态）。CAS 把条件和更新合并成一条原子 SQL：UPDATE ticket SET status='closed' WHERE id=? AND status='pending'，靠数据库行锁保证原子性，影响行数为 0 就说明状态已变。

Q18 这段实习最大的困难？ A：最大的难点不是写代码，是定阈值时没有标准答案。设备"实际在不在线"没有直接的 ground truth——日志只告诉你心跳有没有到。解法是拿两层近似标注：后续人工处理结果 + 后续心跳是否长期恢复，用它们当基准做回放，把 N 从"感觉"变成"数据"。这让我理解工业界"数据驱动决策"是在没有完美答案的场景里逼近答案。

Q19 实习中犯过什么错？ A：巡检任务第一版忘了做幂等，联调时失败重跑，同一台设备重复生成两条告警。修复是给结果表加"设备+规则+时间窗"唯一键，顺手把重试从整片重跑改成 checkpoint 断点续扫。教训：只要存在重试就要先想幂等。

Q20 如果重来，你会改进什么？ A：两点。①防抖阈值当时是全局统一值，其实不同网络环境（商圈/地库/写字楼）丢包差异很大，更优是按设备历史丢包率做个性化阈值或分档配置；②巡检规则和异常检测规则当时是两套配置，后期维护出现不同步，应该统一成一套规则中心的配置源。

Q21 设备量涨 10 倍，巡检系统改什么？ A：分层答：①分片数和 worker 数可配置化，量涨就加片加工人，架构不变；②数据访问从单库查询演进到按分片路由（甚至读从库/物化视图），避免热点；③规则计算从每轮全量优化为增量——只扫自上轮以来有心跳变化的设备；④结果聚合从同步等齐改为流式汇总。

二、中青旅 · 经营问数 Copilot + 智慧文旅问答（AI 应用实习）

Q1 介绍一下中青旅这段实习？ A：我在中青旅科技创新部做 AI 应用研发，围绕两个场景：经营分析问数 Copilot（Text-to-SQL）和智慧文旅问答（RAG）。问数上我把一步生成拆成指标解析、QueryPlan、SQL 构建三段，加指标词典和 AST 校验，218 条回归集上可执行率 76.1%→89.4%；同时参与指标语义治理，建了 126 个核心指标、247 组别名映射。问答上用 Metadata Filter 解决跨景区串召和过期政策误召回，父子 Chunk 加 Rerank 优化召回，Top-5 命中率 80.4%→90.2%。全程建 Badcase 回归评测，7 轮迭代把端到端正确率 78.6%→87.3%。

Q2 为什么把一步生成拆成三段？ A：一步生成是黑盒：错误无规律、不可归因、不可拦截。拆段后每段职责单一，三类错误各有人拦——误映射在词典、漏条件在 Plan 强制、幻觉在模板+AST。而且每段可独立测试优化，出错了能精确定位到段。

Q3 AST 校验具体校验什么？失败了怎么办？ A：用 sqlglot 把 SQL 解析成语法树，核对：表名在 schema 存在、每个字段真属于所查表、必要过滤（时间/组织）存在、无异常嵌套。失败带错误信息重新生成（限 2-3 次），仍失败降级用模板 SQL，保证一定返回可执行结果。

Q4 可执行率和正确率是一回事吗？ A：不是，这是我最注意区分的口径。可执行=语法和对象合法能跑通；正确=口径也对。漏了组织过滤的 SQL 照样能执行、返回一个看着正常的数字——最危险。可执行率能自动化统计所以当主指标，同时人工抽检语义正确率，两者一起看。

Q5 表结构 schema 怎么给模型？全给吗？ A：不全给，表多字段多会超上下文且干扰生成。按问题先检索相关表（表名/描述/字段也做成 Metadata 检索），只把相关表的 schema 放进 Prompt。

Q6 为什么不微调模型，而用 Prompt+链路工程？ A：三个原因：标注数据量不够（Badcase 才百级，微调要千级以上）；微调迭代慢成本高，业务口径还在变；链路工程可解释可干预，出问题能定位到环节，微调是黑盒。且基础模型在迭代，链路方案可平移换模型，微调绑定。

Q7 126 个指标怎么选出来的？ A：三个来源取交集：问数日志高频词、财务核心指标（回款/预算/应收）、三大业务线（景区/酒店/旅行）各自主线指标。先覆盖最高频 126 个，长尾按需扩。

Q8 消歧（多口径指标）具体怎么实现？ A：指标解析段让模型输出"命中指标+置信度"。多口径指标：置信度高→用默认口径，但答案里显式标注"按含税口径"；置信度低→生成澄清问题反问用户，给选项不给开放题。原则：宁可多问一句，不可猜错口径。

Q9 Embedding 用的什么模型？为什么？ A：bge 系列（bge-large-zh-v1.5/BGE-M3），1024 维。理由：中文效果好、开源可私有化部署（央企场景数据不出内网是硬约束）、生态成熟配套 reranker 同系列。

Q10 父子块具体怎么配的？ A：子块约 200 字、按语义段落切（标题/条款边界优先）；父块约 1000-2000 字或完整章节。子块入向量库，块记录 parent_id；命中子块后按 parent_id 取父块（同父的多个子块去重合并）进 Prompt。

Q11 Rerank 用的什么？延迟代价？ A：bge-reranker 交叉编码器。海选 top50→精排取 top5。每条打分几十毫秒，50 条总增量两三秒内可控（可批量并行），换来精度提升明显，值得。

Q12 Metadata Filter 是先过滤还是后过滤？ A：先过滤（pre-filter）：先用结构化条件把候选集缩小到本景区、当前生效，再在缩小集合里做向量检索。反过来先召回再滤，会出现召回 50 条滤完只剩 3 条、数量不足的问题。

Q13 剩下 9.8% 没命中的是什么？怎么办？ A：三类：知识库缺内容（检索再好也无米下锅，补知识库）、问题本身歧义（需澄清）、需要跨文档多跳推理（要 Agent 拆解）。检索优化能解决"找得准"，解决不了"库里没有"。

Q14 正确率（回归集）谁来判？ A：人工标注为主。量大时用 LLM 辅助初判（按评分标准给通过/不通过），但定期人工抽检校准 LLM 判断的一致率——LLM 当裁判本身也会错，只能当初筛。

Q15 两段实习（中青旅 vs 美团）有什么区别和联系？ A：技术底座相同——都是事件/数据链路上的工程问题，方法论一致：Badcase 驱动、先定位根因再改、改动要可验证。区别在问题域：中青旅是 AI 应用的可信度问题（幻觉、口径、召回），美团是分布式系统的稳定性问题（误报、状态一致、幂等）。中青旅教我 AI 工程化，美团教我后端工程素养，我想要的方向正是两者交叉——AI 应用的后端化。

Q16 这段实习最大的困难？ A：Badcase 的归因。同一个错误答案，可能是检索没找到、排进前五但 Prompt 没放好、模型没遵守指令、工具参数错——五环都可能背锅。一开始只看最终答案对错去改，判断错过一次：以为是不瞎编的 Prompt 问题，实际是那批题检索根本没召回。后来养成逐环节留痕的习惯：把检索结果、组装后的 Prompt、工具调用参数都打出来，先定位错在哪一环再动手。

Q17 犯过的错？ A：同 Q16：没做逐环节归因就改 Prompt，一轮迭代白做。教训：AI 链路里"最终答案错"≠"生成环节错"，必须先看中间结果。后来把打印中间态固化成调试规范。

Q18 知识库扩大 100 倍怎么办？ A：①向量库层面：Milvus 分区（按景区/业务线 partition）、HNSW 索引参数调优（efSearch 权衡召回率与延迟）；②检索层面：分层检索——先用轻量分类器把问题路由到业务线，再在子库内检索；③粗召回通道加关键词/混合检索兜底。

Q19 怎么评估一个 RAG 系统的好坏？ A：分层：检索层（Top-K 命中率、MRR）→ 生成层（忠实度：答案是否忠于检索材料）→ 端到端（最终答案正确率）→ 线上（用户反馈率、人工接管率）。只看端到端无法归因，只看检索层会漏生成退化，四层都要有。

Q20 从零建一个问数系统你会怎么排？ A：先治理后智能：①先和业务定核心指标口径、建治理表（没有这个模型再好也映射不对）；②小范围 MVP（十几个指标内）验证链路；③同步建回归集；④逐步扩指标面和问题复杂度。顺序错了（先上模型后治理）会一直在修口径问题。

三、通用收尾题（两段实习都可能被问）

Q1 实习最大的收获？ A：美团——学校做项目只关心跑通，工业界每个改动上线前要回答三个问题：怎么验证（回放）、怎么灰度（按城市逐步放开）、怎么回滚。中青旅——AI 应用的上限取决于数据治理而不是模型，以及没有回归评测的 AI 系统每次改动都是赌博。

Q2 你的优势和这个岗位怎么匹配？ A：两段实习让我同时具备后端工程素养和 AI 应用工程化能力，且都养成了数据驱动、改动可验证的习惯。对开发岗来说，这是能独立从需求做到交付、且产出可衡量的能力。

Q3 你的缺点？ A：实习初期过于追求方案完美、出方案慢，mentor 教我先用最小可行方案验证方向再迭代，后来好很多。
